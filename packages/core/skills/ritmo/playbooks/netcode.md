# Online multiplayer, rollback, and prediction

1. Pick the model. Lockstep runs a tick only once every peer's input for it has arrived: simplest, but it waits on the slowest message. Rollback runs every tick at once with a guess for remote input (the last input confirmed is a good one), and goes back when real input contradicts a guess. Client prediction is rollback with one peer. Ritmo carries no transport: the game sends inputs, saves, and checksums over its own.
2. Make the simulation one schedule every peer ticks the same way, at a fixed step (`Clock`), with randomness in a resource (`Random`) and math from `Ops`. The simulation lint rules enforce these.
3. Feed input through a source service (`InputCapture.system`, or any service with `snapshot()`) that the host fills with the input for the tick being run, keyed by its `Clock` tick. Do not send remote input with `runtime.send`: an event sent after a checkpoint is still unread after rewinding to it, so the ticks run again read it at the first of them, not at the tick it was for.
4. For rollback, take a checkpoint before every tick, `runtime.checkpoint(simulate)`, and keep it by tick. Give `Game.Runtime.make` a `checkpoints` window that covers the longest correction you accept, in ticks.
5. When confirmed input for tick `t` differs from the guess used, `runtime.rewind(` the checkpoint of `t` `)` and tick again up to the present, taking a new checkpoint before each tick. Check the `Result`: `Released` means the correction is older than the window; resynchronize (step 8).
6. Keep `simulate` rewindable. Its systems keep no `local` state, and its services are sources or plain data; anything else does not compile, and the error names the fix. A sound, a particle, or a message to a server is an event or a resource the simulation writes and host code outside `simulate` acts on.
7. Host code outside `simulate` does not rewind. Renderers (`RenderSync`) and readouts see a rollback as ordinary changes, and need nothing special. Events they read are published again for ticks run again: act on events of confirmed ticks only, or de-duplicate them by `Clock` tick and a key.
8. To let a player join or resynchronize, one peer saves (`runtime.snapshot()`) at a tick and every peer restores that same save at that tick. A runtime that restores starts its readers over, so one that restores and one that plays on do not agree.
9. Exchange `runtime.checksum()` of confirmed ticks to catch a desync as soon as it happens. Equal worlds give equal checksums on every device.

**Done when** a headless test plays two peers over a fake link with latency and reordering, seeded so it fails the same way again, and each ends with the checksum of one runtime given every input, after more than zero rewinds.
