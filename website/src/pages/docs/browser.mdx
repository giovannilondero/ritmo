The simulation never touches the page. The page is a **host**: it turns
animation frames into fixed steps, turns key presses into input the systems
read, and draws the world after each frame. `@typeonce/ritmo-browser`,
`@typeonce/ritmo-render`, and `@typeonce/ritmo-pixi` hold that glue.

This is the result: the top-down game from the repository, whose rules are
the same headless schedules its tests run, with a Pixi renderer on top.

## The loop

`FixedLoop.start` runs the game at a fixed step whatever the frame rate. Each
animation frame adds its time to an accumulator; the loop runs as many
updates as fit, then calls `render` once. Long frames are clamped, so a tab
that was in the background does not run a minute of game at once.

```ts twoslash
import { Clock, Descriptor, Schema } from "@typeonce/ritmo"
const Game = Schema.bind(Schema.fragment({ components: { Tag: Descriptor.Component<{}>()("Example/Tag") } }))
const update = Game.Schedule()
const runtime = Game.Runtime.make({ services: Game.Runtime.services() }).value!
declare const draw: (alpha: number) => void
// ---cut---
import * as FixedLoop from "@typeonce/ritmo/FixedLoop"
import { BrowserTickSource } from "@typeonce/ritmo-browser"

const loop = FixedLoop.start({
  source: BrowserTickSource.make(window),
  step: Clock.hz(60),
  maxFrameSeconds: 0.25,
  maxStepsPerFrame: 5,
  update: () => runtime.tick(update),
  render: (frame) => draw(frame.alpha),
  onFailure: (failure) => console.error(failure)
})
```

The source is just "frames, with the time between them". In a native shell
or a renderer with its own ticker, wrap that ticker with `FixedLoop.source`
instead, and the rest stays the same.

## Input

Input is declared once as a set of **actions**, then bound per device. The
keyboard and the gamepad merge into one source, and the systems only ever see
actions, never keys.

```ts twoslash
import { Descriptor, Schema } from "@typeonce/ritmo"
// ---cut---
import { Controls, Gamepad, InputCapture, Keyboard } from "@typeonce/ritmo-browser"

const Actions = Controls.actions(["left", "right", "jump"])

const keys = { left: ["ArrowLeft", "a"], right: ["ArrowRight", "d"], jump: [" ", "w"] } as const
const buttons = { left: ["dpadLeft"], right: ["dpadRight"], jump: ["south"] } as const

const makeControls = (devices: {
  readonly keyboard: Keyboard.Actions<typeof keys>
  readonly gamepad: Gamepad.Actions<typeof buttons>
}) => Actions.merge(devices)

// The input source is a service; each update copies its snapshot into a resource.
const ControlsInput = Descriptor.Service<ReturnType<typeof makeControls>>()("Example/Controls")
const Input = Descriptor.TransientResource<InputCapture.SnapshotOf<typeof ControlsInput>>()("Example/Input")
```

`InputCapture.system` makes the system that takes the snapshot at the start
of each update, so every system in that step sees the same input:

```ts twoslash
import { Descriptor, Schema } from "@typeonce/ritmo"
import { Controls, Gamepad, InputCapture, Keyboard } from "@typeonce/ritmo-browser"
const Actions = Controls.actions(["left", "right", "jump"])
const keys = { left: ["ArrowLeft", "a"], right: ["ArrowRight", "d"], jump: [" ", "w"] } as const
const buttons = { left: ["dpadLeft"], right: ["dpadRight"], jump: ["south"] } as const
const makeControls = (devices: { readonly keyboard: Keyboard.Actions<typeof keys>; readonly gamepad: Gamepad.Actions<typeof buttons> }) => Actions.merge(devices)
const ControlsInput = Descriptor.Service<ReturnType<typeof makeControls>>()("Example/Controls")
const Input = Descriptor.TransientResource<InputCapture.SnapshotOf<typeof ControlsInput>>()("Example/Input")
const Game = Schema.bind(Schema.fragment({ resources: { Input } }))
// ---cut---
const CaptureInput = InputCapture.system(Game, {
  name: "Example/CaptureInput",
  source: ControlsInput,
  resource: Input
})

const Jump = Game.System(
  "Example/Jump",
  { resources: { input: Game.System.readResource(Input) } },
  ({ resources }) => {
    const input = resources.input.get()
    if (input.actions.jump.pressed) {
      //                  ^?
    }
  }
)
```

In the page, the devices read the window: `Keyboard.actions(window, keys)`
and `Gamepad.actions(window, buttons)`. In a test, the same bindings play a
script instead, `Keyboard.scripted(keys, [{ frame: 0, press: ["jump"] }])`,
so a test presses keys frame by frame with no browser. Pointer and on-screen
touch controls work the same way (`Pointer`, `Touch`).

## Rendering

`RenderSync.system` keeps one renderer node per entity: it creates a node
when an entity gets the renderable component, re-applies it when the
transform changes, and destroys it when the entity goes. You say what a node
is; Ritmo does the bookkeeping. This is the wall renderer of the game above:

```ts twoslash
import { Descriptor, Schema } from "@typeonce/ritmo"
const Position = Descriptor.Component<{ x: number; y: number }>()("TopDown/Position")
const Collider = Descriptor.Component<{ width: number; height: number }>()("TopDown/Collider")
const Wall = Descriptor.Component<{}>()("TopDown/Wall")
const Game = Schema.bind(Schema.fragment({ components: { Position, Collider, Wall } }))
// ---cut---
import { RenderSync } from "@typeonce/ritmo-render"
import type { NodeRegistry } from "@typeonce/ritmo-render"
import { Graphics } from "pixi.js"

const WallNodes = Descriptor.Service<NodeRegistry.NodeRegistry<Graphics>>()("TopDown/WallNodes")

const RenderWalls = RenderSync.system(Game, {
  name: "TopDown/RenderWalls",
  renderable: Wall,
  transform: Position,
  registry: WallNodes,
  select: { collider: Game.Query.read(Collider) },
  create: ({ data }) => {
    const { width, height } = data.collider.get()
    return new Graphics().rect(-width / 2, -height / 2, width, height).fill(0x262a31)
  },
  apply: (node, { transform }) => node.position.set(transform.x, transform.y)
})
```

The system depends on a generic `NodeRegistry` service, not on Pixi. The
page provides Pixi's implementation when it makes the runtime:

```ts
Game.Runtime.service(WallNodes, PixiNodeRegistry.make(wallLayer))
```

Swap that line for a Three.js registry (`NodeRegistry.make({ attach, detach })`)
and the same systems draw in 3D. The simulation names no renderer at all, so
its tests never load one.
